### Bugs found while building, worth remembering

- **The `date` cast writes a time component.** `protected $casts = ['week_start' => 'date']`
  stores `"2026-07-23 00:00:00"`. MySQL truncates it in a DATE column so nothing looks wrong,
  but the stored value then never equals a `Y-m-d` string in a `where`, so
  `WeekLock::firstOrCreate(['week_start' => …])` missed its own row and hit the unique index.
  SQLite keeps the time and fails loudly, which is how it surfaced. Every DATE column is now
  cast `date:Y-m-d`. This was latent in the design, not something the rewrite introduced.
- **`TeamFactory::configure()` collided with Laravel's factory hook.** `configure()` is called
  from the factory constructor; defining it as a state method *and* calling `->configure()`
  registered the `afterCreating` twice and duplicated the `team_settings` row. Folded into the
  real hook.
- **`AssignmentFactory` paired a team with another team's position.** Two independent
  `Team::factory()` calls in one definition produce two teams, and the
  `(team_id, position_id)` composite FK rejected the row. `team_id` is now derived from the
  generated position. The constraint did its job; the failure was just opaque.

### Security holes closed

- `routes/api.php` exposed `GET /api/shifts` and `POST /api/shifts/bulk` with **no
  authentication and no team scoping**, taking `user_id` from the query string. Anyone could
  read or overwrite anyone's worked hours. Both routes deleted; the replacements live inside
  the `tenant` group and only touch the caller's own rows unless an admin asks otherwise.
  `resources/js/app.js` still calls the old paths, so the hours screen is broken until the JS
  pass — that is the correct trade.
- `Media::download` now streams through the app and honours `is_visible`; previously an
  invisible file was still fetchable by guessing its `public`-disk URL.
- `StoreAssignmentRequest` scopes `position_id` to the current team, so a borrowed id is a
  validation error rather than a database error.

### Decisions taken that were not in the plan

- **Current team is bound into the container** by `SetCurrentTeam`
  (`app()->instance(Team::class, $team)`), so controllers type-hint `Team` and form
  requests/Livewire call `app(Team::class)`. Chosen over passing a request attribute around
  because it removes the accessor from every call site. Consequence to know about: outside the
  `tenant` group the container would happily build an empty `Team`, so anything reading it
  must sit in that group.
- **`Admin\UserController::destroy` deactivates instead of deleting.** `shifts.user_id` and
  `rates.user_id` are RESTRICT, so deleting anyone who has ever worked would throw. Matches
  what `is_active` was introduced for.
- **`week_lookahead` clamps forward navigation only.** Bounding the past as well would stop
  admins reviewing previous weeks, which the lookahead setting was never about.
- **Absences and per-person signup counts are admin-only in `CalendarService`**, preserving
  the legacy privacy boundary — absence reasons are free text.
- **`PendingMemberCountComposer` dropped the 15-minute cache** the old composer had. It needed
  invalidating from three separate places and still went stale; one indexed COUNT per admin
  page view is cheaper to maintain than that was.
- **`logout` became POST** (`/odhlasenie`). It was a GET, which any prefetch or crawler could
  trigger.

### Cleanups done that were not strictly in scope

- Repointed the four error views and both nav partials from the removed `bugreport.index`

### Tenancy hole found while doing it

Livewire's `/livewire/update` is its own route and only re-runs middleware registered as
**persistent**. Auth is on that list by default; `SetCurrentTeam` and `EnsureUserIsActive` were
not. So the first page load was team-scoped but every subsequent Livewire action ran with no
team in the registrar — `BelongsToTeam` stops filtering, `app(Team::class)` builds an empty
model, and a component reads and writes across every cinema. **It fails open**, which is the
bad direction. Registered via `Livewire::addPersistentMiddleware()` in `AppServiceProvider`.

This already affected `UserTable`, written earlier the same day. The tests did not catch it
because `Tests\TestCase::tenant()` sets the container binding itself, so the middleware never
had to run. Worth remembering: a green Livewire test does not prove the tenant context is
established in production.

### Design decisions

- **Position is chosen per day card, not once per week.** The old UI had a single shared "Extra
  info" text box at the top; the natural translation would have been one shared position
  selector. Rejected: working Bufet Thursday and Pokladňa Friday is normal, and a per-card
  select keeps each component self-contained with no shared parent state to synchronise. The
  shared text box became a per-card note, which is how `assignments.note` is now reachable.
- **Each card loads its own assignments** rather than receiving a slice of a shared collection.
  Seven indexed `(team_id, date)` lookups beat keeping one collection in sync with seven
  independently re-rendering components. `CalendarService` therefore no longer fetches
  assignments at all — it hands down `positionOptions` instead.
- **Dropdowns show `positions.name`, badges show `label()`.** `label()` prefers the short code,
  which is right for the compact row badge but made the selects read "UV, BUF, POK, VED". Only
  noticed by loading the real page — the test asserting `BUF` had happily passed.
- **Positions already taken that day are filtered out of the select**, so the unique
  `(user, date, position)` key cannot be reached by clicking. `signUp()` still re-checks the
  policy, so a replayed Livewire request against a locked week is refused, not just hidden.
- **`logout` is POST**, so both nav partials needed a form. Extracted `x-logout-button` rather
  than duplicating the CSRF form twice.
- **The names toggle moved to a `hide-names` class on `<html>`** plus one CSS rule. It used to
  set `display:none` on each row with jQuery, which a Livewire re-render throws away.

### Deleted

`components/one-day`, `day-user-list`, `day-user-row`, `day-button`, `partials/_extratext`, and

the page, and `tommyside@centrum.sk` / `asdasd` reaches the calendar with admin controls.

### Three separate problems behind "display error on login"

1. **The error was only a toast.** `LoginController` flashed `['error' => …]`, which
   `x-flash-message` renders bottom-right and deletes after three seconds — the wrong place and
   the wrong lifetime for "your password was wrong". The credential failure is now attached to
   the `email` field via `withErrors()`, so `x-form-input`'s existing `@error` block renders it
   inline under the field. A new `x-alert` component shows `session('error')` as a persistent
   box on the form, which is what the middleware's blocked/unverified messages need.
2. **The toast could silently render nothing.** `x-flash-message` interpolated messages into a
   JS single-quoted string inside an Alpine `x-init` attribute:
   `addToast('{{ session('error') }}', …)`. One apostrophe in a message breaks the whole
   expression and no toast appears at all. Switched to `@json(...)`. Latent, not yet triggered
   by the current Slovak strings — but it would have been by the first one with an apostrophe.
3. **A regression I introduced yesterday.** `LoginController` folded `is_active => true` into
   the credentials so a blocked account failed at the form. Side effect: a blocked user is told
   "wrong password", and `EnsureUserIsActive`'s accurate messages ("Účet je zablokovaný.",
   "Ešte si nebol/a overený…") became unreachable, because such a user could never authenticate
   to hit the middleware. Reverted to email+password only. The middleware runs on the next
   request and ejects them with the real reason, so there is one place deciding who gets in and
   one accurate message. Marginally more information disclosure than a generic failure, which
   is the right trade for a small internal tool and matches what the legacy app did.

### Order-dependent test failures — worth knowing about

Two `LoginTest` cases failed in the suite but passed in isolation. Cause: **the rate limiter's
counters live in the cache and the array store survives between tests in one process**, so
`throttle:6,1` on `login.auth` accumulated across test methods and started returning 429 for
reasons unrelated to the test under test. Proved it with a probe: three POSTs in one test, then
the second test's second POST already 429s.

Fixed with `Cache::flush()` in `TestCase::setUp()` rather than per-class, so any future test
touching a throttled route (login, `shifts.store`, `rates.store`) does not flake. This is the
kind of failure that looks like a real bug and only appears in certain orderings.

Suite is now 39 tests / 107 assertions, green. Pint clean, assets rebuilt (the new `x-alert`
classes needed a Tailwind pass).

## 13:20 — Drop position choosing, shared note, visual pass

User logged in, then asked to remove the per-day position dropdown, bring back a single shared

### Schema consequence, and a reversal to be aware of

Removing the position picker means nothing supplies `assignments.position_id`, which was
NOT NULL. Two migration edits:

- `position_id` → **nullable**. NULL honestly means "not decided yet"; an admin fills it in when
  building the plan. The composite `(team_id, position_id)` FK still guarantees a set position
  belongs to the same team, it just is not enforced while NULL.
- `unique(user_id, date, position_id)` → **`unique(user_id, date)`**. One signup per person per
  day, which is what a single button means. Keeping the old index would have given *no*
  protection with a nullable column — MySQL treats NULLs as distinct, so a double-clicked button
  inserts two rows.

**This reverses doc 20 §7's "same user, same day, two different positions ⇒ accepted".** That
only made sense while signup chose a position. Flagged in doc 21 §4 with the note that
`unique(user_id, date)` is the index to widen if per-position assignment returns with Filament.

### The shared note

`App\Livewire\ExtraNote` holds it in the **session**, not as a prop passed to the seven cards.
That is what makes it survive week navigation and a reload, gives "stays until cleared" for
free, and stops every keystroke re-rendering seven components. `DayCard::signUp()` reads it back
from the session. Verified end to end over real HTTP: set the note through the ExtraNote
component, fire `signUp` on a card, and the row came out with `note = 'od 15:00'`,
`position_id = NULL`, correct `team_id`.

First attempt was a full-width textarea in its own card; user asked for it small and inline, so
it is now a single-line input beside the names toggle with the clear X *inside* the field.

### Visual pass

— wrong ramp and too light for cards to read as raised), indigo primary, semantic colours for
state only, `text-sm` body, `font-medium`/`font-semibold` over `font-bold`, `max-w-7xl` with
standard gutters, `gap-*` not margins, `min-h-11` touch targets, mobile-first (one column, 7-up
from `xl`).

`partials/_adminbutton` and `_nonadminbutton` **deleted** — collapsed into one toolbar in
`calendar/index`. The second was a hand-rolled duplicate of the same files modal
`_fileuploadmodal` already provides, and `_fileupload` already gates the upload form on admin,
so one include serves both roles.

The app stays **single-theme dark**; doc 19 wants dark-default *with* a light variant, and that
dual-theme work is not done.
